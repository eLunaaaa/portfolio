# 설계 선택 — 무엇을, 왜 선택했는가

[프로젝트](../../README.md) · [모듈별 문서](README.md) · [소스](../../source/README.md)

이 프로젝트에서 중요하게 본 기준은 **검출 점수 하나를 높이는 것보다, 사고가 나면 필요한 영상이 남고 장애 후에도 연결해서 볼 수 있는가**였습니다. 아래는 구현에서 확인되는 선택과 그 이유를 정리한 것입니다. 성능을 측정하지 않은 대안에 대해 우열을 실측했다고 주장하지 않습니다.

## 선택을 먼저 보기

| 문제 | 비교한 접근 | 선택·이유 | 받아들인 비용 | 코드·상세 |
|---|---|---|---|---|
| 모든 주변 영상을 저장·전송하면 자원이 큼 | 전체 전송 / 단일 AI 선별 / 위치·화각 후 AI | 팀의 1차 Filter 뒤에 대상 차종 판정을 연결해 불필요한 영상 처리를 줄임 | 1차 선별에서 빠진 영상은 AI로 복구할 수 없음 | [AI 연동](AI_HANDOFF.md) |
| 실장치와 학습 입력 불일치 | 일반 사전학습 모델 그대로 / 모형차 fine-tuning | 실제 촬영·라벨 검수·Tiny fine-tuning, 고정 전처리 계약 | 수집·검수 비용과 제한된 차종 범위 | [학습](MODEL_TRAINING.md) |
| 연속 프레임 평가가 과대평가될 수 있음 | 프레임 무작위 / 촬영 묶음 분리 | 원본·촬영 세션 계열을 하나의 split으로 관리 | 목표 70/15/15의 정확한 프레임 비율을 포기 | [학습 split](MODEL_TRAINING.md) |
| 한 번의 검출 흔들림 | 단일 프레임 / 전 프레임 / 일정 간격 다수결 | 팀 런타임의 6프레임 sampling·최근 3회 중 2회 검출 | 짧게 보이는 대상의 미검출 가능성 | [AI 판정](AI_HANDOFF.md) |
| 촬영 중 추론·저장이 오래 걸림 | callback에서 모두 수행 / 별도 Worker와 Snapshot | 긴 작업과 촬영을 분리하고 Snapshot 참조 수명 보호 | Queue·버퍼 수명 관리 복잡성, 약 422MiB 프레임 공간 | [AI 보존](AI_HANDOFF.md) |
| 프로세스는 살아도 업무가 멈춤 | PID 감시 / 감시 thread heartbeat / 업무별 진행 감시 | 업무 진행 deadline이 살아 있을 때만 systemd watchdog 통지 | 정상 최대 작업 시간에 맞춘 기한 설계 필요 | [Fail-safe](../FAILSAFE.md) |
| 인터넷 단절 때 증거 유실 | 즉시 실패·폐기 / 메모리 재시도 / 영속 큐 | 디스크 보존·backoff·복구 후 전송 | 디스크 소비와 큐 운영 필요 | [Uploader 계약](UPLOADER_CONTRACT.md) |
| ACK가 유실되면 완료 여부 불명 | 무조건 재전송 / HTTP 성공만 확인 / 저장 상태·해시 확인 | 로컬 인계 ACK와 서버 저장 ACK 분리, 멱등 확인 | 조회·상태 전이·해시 비용 | [ACK 경계](UPLOADER_CONTRACT.md) |
| 차량 간 동시 시작이 불가능 | 도착 순서 병합 / 시간 기준 병합 | 공통 NTP·Chrony 상태와 촬영 시각 기반 trim/pad | 네트워크 시각 오차·구간 미겹침 처리 | [Time Sync](TIME_SYNC.md) · [서버](SERVER.md) |
| 늦은 차량을 언제까지 기다릴지 | 무한 대기 / 고정 수집 후 영구 종료 / 수집 창+revision | 첫 영상 후 12초, 최소 1개로 생성하고 늦게 오면 재병합 | 재인코딩 비용·여러 버전 저장 | [서버](SERVER.md) |
| 검증 안 된 장치 배포 위험 | 소스 복사 후 현장 빌드 / 매 push 운영 반영 / 검증 artifact 수동 승격 | main의 성공 CI와 같은 SHA를 골라 canary·순차 배포 | 장치별 smoke 시간과 운영 준비 | [CI](CI.md) · [CD](CD.md) |
| 모형차 시연 규모의 저장 관리 | 외부 DB·분산 큐 / 로컬 SQLite+파일 | 설치가 단순한 SQLite와 파일 기반 job으로 시작 | 수평 확장·다중 Worker 운영에는 추가 설계 필요 | [서버](SERVER.md) |

## 설계 기여를 읽는 기준

- **직접 담당 구현:** 모델 학습 도구, 서버·웹, Time Sync, 초기 CI/CD.
- **전체 구조 설계:** Fail-safe 계층, 완료 신호와 보존·재시도 경계.
- **팀과 연결한 구현:** 카메라·AI 런타임, 공통 watchdog, Sensor·Filter·V2V·Uploader. 팀 코드의 선택은 담당 설계와 연결된 동작으로 설명하고 개인 단독 구현으로 표시하지 않습니다.

각 상세 문서는 ‘문제와 제약 → 선택과 대안 → 동작·상태 → 실패·복구 → 검증 → 한계’를 같은 순서로 사용합니다.
